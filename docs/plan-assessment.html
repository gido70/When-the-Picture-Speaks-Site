الدمج والاستقرار على Windows قبل أي ميزة جديدة: صحيح تمامًا. البناء فوق نسخة غير مثبتة على Windows يضاعف الأخطاء.

الاستيراد من الأدوات الخارجية

صحيح، وهو أذكى من محاولة دمج كل مولّد داخل البرنامج. Google Flow وغيره تُستخدم خارجيًا، والاستوديو يجمع ويزامن ويصدّر.

فصل الموقع عن المحرك

صحيح. الموقع ثابت تعريفي، والمحرك خاص ومحلي.
ثلاث نقاط تحتاج تصحيحًا

1. ثبات ملامح الشخصيات ليس وظيفة في محركنا

المحرك لا يولّد صورًا. بطاقة الشخصية تستطيع حفظ الصور المرجعية والوصف والبرومبت لتُستخدم في أداة خارجية، لكنها لا تضمن ثبات الملامح. الثبات يتحقق في أداة التوليد، أو برسم يدوي، لا في الاستوديو.

2. أصوات الأطفال غير متاحة مجانًا بجودة مقبولة

Edge TTS لا يقدم أصوات أطفال عربية؛ أصواته العربية لبالغين فقط. رفع طبقة صوت بالغ يعطي صوتًا مصطنعًا. الخيارات الواقعية: تسجيلات حقيقية بأصوات أطفال (بموافقة أوليائهم)، أو خدمة مدفوعة تدعم تصميم الأصوات، بموافقتكم.

3. سرعة الإنتاج عائق قبل القصص

فيديو مدته 3:35 استغرق نحو 35 دقيقة، ومعظمها في رسم الترجمة إطارًا إطارًا. القصة متعددة الشخصيات فيها أسطر حوار أكثر بكثير، فسيتضاعف الزمن. يجب حل هذا في المرحلة الأولى لا بعدها.
المرحلة الثانية أكبر مما تبدو

ما تضمه فعليًا

نموذج مشروع جديد، وسجل شخصيات، ومحرر حوار، وتوليد صوت لكل سطر، ودعم مقاطع الفيديو داخل المشاهد، واستيراد بحقوقه، وحفظ واستكمال. هذه خمس وحدات على الأقل.

ما ينقص المحرك الحالي تحديدًا

مسار المشاهد الحالي يعرض صورًا فقط. المقاطع المتحركة المستوردة من Flow تحتاج دعمًا جديدًا في التجميع (قص، ومدة، وصوت المقطع نفسه).

تحسينات المحرك القائم

دعم مقاطع الفيديو في مسار المشاهد؛ رسم الترجمة بطريقة أسرع؛ إظهار التشكيل؛ وفصل النص المنطوق عن الظاهر.

الأماكن

app/services/video.py وalignment.py وtimeline.py، بتعديلات محدودة ومختبرة.
ما يحتاج وحدات مستقلة
مجلد جديد app/studio/ لا يمس مسار الإنتاج القديم:

project.py

قراءة المشروع وحفظه وترقية صيغته ونسخه الاحتياطية.

characters.py

بطاقات الشخصيات: الاسم، والصور المرجعية، والوصف، والصوت الافتراضي (صوت Edge أو عينات مرفوعة)، والفئة العمرية.

dialogue.py

تحويل أسطر الحوار إلى صوت لكل سطر وتوقيت، ثم إلى مشاهد وترجمة.

assets.py

استيراد الصور والأصوات والمقاطع الخارجية مع بيانات مصدرها وحقوقها.

صفحات الواجهة

صفحات Streamlit منفصلة: «الشخصيات»، و«المشاهد والحوار»، و«المشاريع»، بجانب الصفحة الرئيسية وصفحة المزامنة الحالية.
مكان ملفات المستخدممهم
أقترح نقل المشاريع والمخرجات من داخل مجلد البرنامج (storage/) إلى مجلد مستقل مثل Documents\WhenThePictureSpeaks. هكذا لا يمكن لأي تحديث أو حذف لمجلد البرنامج أن يمس أعمالكم.
لماذا لا قاعدة بيانات الآن
ملفات JSON لكل مشروع تكفي لعشرات المشاريع، وهي قابلة للقراءة والنسخ والمراجعة في GitHub. قاعدة بيانات SQLite تُدرس فقط إن تجاوز العدد المئات أو احتجتم بحثًا متقدمًا.

تحديث Windows من GitHub بأمان

نعم، ممكن بأمان، بشرط فصل ملفات المستخدم عن ملفات الشيفرة.

الطريقة الموصى بها: نسخة Git رسمية واحدة

الإعداد مرة واحدة

تثبيت Git for Windows (يتضمن مدير بيانات الاعتماد لتسجيل الدخول إلى المستودع الخاص)، ثم استنساخ المستودع في مجلد رسمي واحد، مثل C:\WhenThePictureSpeaks\studio. النسخ القديمة تُؤرشف ولا تُحذف.

الإصدارات المعتمدة فقط

كل إصدار معتمد يُوسم في GitHub بوسم مثل v1.6.0. أداة التحديث لا تنزّل إلا الوسوم المعتمدة، لا آخر تعديل في أي فرع.
أداة Update-Studio.bat
زر واحد بدل أوامر CMD:

1. فحص

تعرض الإصدار الحالي وآخر إصدار معتمد. إن وُجدت تعديلات يدوية في ملفات الشيفرة تتوقف وتسرد الملفات، دون أن تغيّر شيئًا.

2. حفظ

تحفظ نسخة من config.toml، وتسجّل الإصدار الحالي للرجوع إليه.

3. تحديث

تنتقل إلى الوسم الجديد، وتثبّت المكتبات فقط إن تغيّر ملف المتطلبات، داخل بيئة المشروع وحدها.

4. اختبار

تشغّل اختبارات سريعة. إن فشلت ترجع تلقائيًا إلى الإصدار السابق.

5. لا مساس بالملفات الخاصة

config.toml والمفاتيح وstorage/ ومجلد المشاريع غير متتبَّعة في Git أصلًا، فلا يكتب عليها التحديث.
ما يجب التحقق منه قبل اعتمادها

ملف .gitignore

التأكد من أنه يستثني config.toml و.venv وstorage/ وأي ملف مفاتيح.

بيئة Python واحدة

المشغّل الحالي لديكم يستخدم Python العام. يجب توحيدها في .venv داخل المجلد الرسمي حتى تكون المكتبات المثبتة هي المختبرة.
البديل: ملفات الإصدار المضغوطة
تنزيل حزمة الإصدار من GitHub Releases. أبسط، لكن المستودع خاص فيحتاج رمز وصول محفوظًا على الجهاز، والرجوع إلى الإصدار السابق أصعب. لذلك أوصي بطريقة Git.
